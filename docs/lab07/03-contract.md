# Контрактне тестування (Р-24)

**Споживач** (`contract/test_dean_consumer.py`): дві взаємодії від імені сервісу деканату — «студент з id 1 має оцінки» і «студент з id 5 не має оцінок». Кожен тест викликає справжній `fetch_student_card` проти сервера-імітації Pact і перевіряє `StudentCard` за Р-24. Тіло описано матчерами (`match.str`, `match.number`, `match.regex` для `funding` і заголовка `Authorization`): провайдер може повернути іншого студента з тими самими типами полів. Фікстура модуля видаляє теку `pacts/` лише один раз, а кожен тест додає свою взаємодію, тож файл [`pacts/dean-office-student-portal.json`](../../app/tests/lab07/contract/pacts/dean-office-student-portal.json) містить **обидві** взаємодії (перевірено: `interactions` — 2).

**Провайдер** (`contract/test_portal_provider.py`): `Verifier` відтворює запити з файлу контракту до справжнього API (фікстура `base_url`). Обробники станів нічого не готують: студенти 1 і 5 уже є в `data/group.json`.

| Взаємодія | Тест споживача | Перевірка провайдера | Причина відмови | Хто змінює і що | Issue |
|-----------|----------------|----------------------|-----------------|-----------------|-------|
| Картка студента з оцінками | пройдено | не пройдено: `$ -> Actual map is missing the following keys: funding` | Р-23 визначає відповідь з *рівно* полями `id, first_name, last_name, email, group, average`, а Р-24 використовує ще `funding`; API виконує Р-23 | Специфікація: замовник має вирішити — додати `funding` у Р-23 (тоді змінює команда API, а тести схеми `STUDENT_SCHEMA` оновлюються) або прибрати `budget` з картки в Р-24 (змінює команда деканату) | [#50](https://github.com/lerabo/testing-course-bondarchuk/issues/50) |
| Картка студента без оцінок | не пройдено: `TypeError: unsupported format string passed to NoneType.__format__` | не пройдено: та сама відсутність `funding` | 1) клієнт деканату форматує `average: null` як число замість «-» (Р-24); 2) див. вище | 1) споживач — команда деканату виправляє `fetch_student_card`; 2) специфікація | [#49](https://github.com/lerabo/testing-course-bondarchuk/issues/49), [#50](https://github.com/lerabo/testing-course-bondarchuk/issues/50) |

Обидва тести позначено `xfail(strict=True)`. Контракт показав відмову, яку не знайшов би жоден із наявних тестів окремо: тести API перевіряють Р-23 і проходять, тест клієнта `tests/test_dean_client.py` підставляє відповідь з `funding` і теж проходить — проблема видна лише на межі між двома командами. На відміну від інтеграційного тесту двох запущених сервісів, контракт перевіряє кожну сторону окремо й незалежно: споживач — проти імітації, провайдер — проти записаного файлу.
