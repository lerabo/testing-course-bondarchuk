# Нестабільність

**Експеримент** (`app/tests/lab08/test_flaky.py`): один сценарій — адміністратор додає студента — по 20 повторів у двох варіантах перевірки повідомлення «Студента додано: Нестабільний Тест». Запуск у GitHub Actions (Chromium headless) з `FLAKY_DEMO=1`; без цієї змінної обидва тести пропускаються, щоб наївний не робив CI червоним, а 40 додаткових студентів не сповільнювали набір.

| Тест | `PORTAL_MAX_DELAY` | Впало з 20 | Причина | Як виправлено |
|------|--------------------|------------|---------|---------------|
| `test_naive_text_right_after_click` | 0 | 20 | `click()` повертається, щойно подію натискання доставлено, а повідомлення з'являється лише після відповіді `POST /api/students` (асинхронний `fetch`). `text_content()` читає значення один раз — у цей момент воно ще порожнє: `assert '' == 'Студента дод...'` | `expect(...).to_have_text(...)` |
| `test_naive_text_right_after_click` | 0,3 | 20 | Те саме; затримка лише збільшує вікно, в якому текст ще порожній | — |
| `test_web_first_assertion` | 0 | 0 | `expect` повторює перевірку, доки текст не з'явиться або не мине тайм-аут | — |
| `test_web_first_assertion` | 0,3 | 0 | Те саме; запуск триває довше (37 с проти 10 с), бо кожен сценарій чекає випадкову затримку API | — |

Наївна перевірка падала навіть без затримки: навіть локальний запит до API займає кілька мілісекунд, а Python читає текст одразу після кліку. Тест, що «інколи проходить», тут не з'явився лише тому, що вікно гонки завжди на боці браузера; на повільнішому комп'ютері чи з кешем той самий тест міг би проходити — це і є нестабільність.

**Увесь набір із затримкою.** `PORTAL_MAX_DELAY=0.3 uv run pytest tests/lab08/test_ui.py` тричі поспіль: щоразу 18 passed, 9 xfailed (66–69 с), так само як без затримки. Відмінностей між запусками немає, тож нестабільних тестів не знайдено. Цього досягнуто тим, що набір від початку уникає двох типових причин:

- дія або підрахунок до завантаження даних: кожен вхід завершується `wait_loaded()` (лічильник «Усього: N»), і лише після цього тести читають `total.text_content()` для порівняння «до/після» (`test_add_student`, `test_delete_after_confirmation`); картка — `StudentCard.wait_loaded()`;
- перевірка «нічого не сталося»: замість `not_to_have_text` чи «рядок ще видно» відразу після «Скасувати» тест чекає позитивної ознаки — запиту наступної дії користувача (див. `01-scenarios.md`).

Найближчий до нестабільності випадок трапився з порядком фікстур (студента створювали після завантаження списку, `01-scenarios.md`) — він падав щоразу, тобто був детермінованим, і виправлений до експерименту.
