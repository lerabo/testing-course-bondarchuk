# Продуктивність: k6

Вимога НФ-продуктивність: `GET /api/students` для потоку з 300 студентів (`data/stream.json`) - p95 ≤ 300 мс за 20 запитів/с, помилок < 1 %. Сценарій `perf/load.js` - відкрита модель (`constant-arrival-rate`): k6 запускає 20 ітерацій щосекунди незалежно від того, чи повернулися попередні відповіді, тож повільний сервер не може сам знизити собі навантаження, як у закритій моделі з фіксованою кількістю віртуальних користувачів. Пороги з вимоги записано в `thresholds`, тому порушення - код виходу 99.

**Середовище.** GitHub Actions ubuntu-latest, AMD EPYC 9V74, 4 ядра; k6 2.3.0 у Docker і сервер (`uv run student-portal-api`, один процес uvicorn, Python 3.14) на одній машині, `--network host`. Сервер перезапускався перед кожним прогоном: запити, які k6 покинув за тайм-аутом, сервер усе одно виконує, і наступний прогін почався б з черги. [Запуск із вимірами](https://github.com/lerabo/testing-course-bondarchuk/actions/runs/45183201816).

**Межа і закон Літтла.** Один запит виконується за R ≈ 0,106 с, а сервер обробляє запити по одному: обробник синхронний, і хоча FastAPI запускає його в пулі потоків, обчислення на Python тримають GIL. Тож пропускна здатність X ≤ 1 / R ≈ 9,4 запиту/с. До 7 запитів/с завантаження ρ = λ·R ≈ 0,74, черги майже немає, і p95 дорівнює часу одного запиту. За 10 запитів/с ρ > 1: сервер виконав 9,19 запиту/с, решта стала в чергу, і за законом Літтла (L = λ·W) час очікування росте разом із чергою - p95 2,83 с. За 20 запитів/с у черзі щосекунди додається ~10 запитів, за 30 с час відповіді досягає тайм-ауту k6 (10 с), а сервер і далі видає ті самі 9,15 запиту/с. Найбільший темп, за якого пороги виконуються, - 7 запитів/с з перевірених; теоретична межа - ~9 запитів/с, вимога - 20. Той самий тест на `data/group.json` проходить з p95 2 мс: 8 студентів замість 300, а час росте квадратично.

**Причина в коді.** Профіль `cProfile` (5 запитів через `TestClient`) - 453 000 викликів `Student.average` і `statistics.fmean`, тобто ~90 600 на запит; на них припадає 1,05 з 1,52 с. Джерело - `rank()` в `api.py`: для кожного з 300 студентів `1 + sum(1 for other in group if (other.average() or 0) > average)` заново рахує середнє всіх інших, O(n²) = 90 000 обчислень середнього на один список. Виправлення - порахувати середні один раз і визначати місце за відсортованим списком (O(n log n)); очікуваний час запиту - одиниці мілісекунд, як на `group.json`, і запас до 20 запитів/с більший за порядок. Issue [#84](https://github.com/lerabo/testing-course-bondarchuk/issues/84).
